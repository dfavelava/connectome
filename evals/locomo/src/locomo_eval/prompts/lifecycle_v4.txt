Each memory must make sense on its own, months later, to someone who has not read the conversation.

Before writing anything, you looked up what is already stored. Check every memory you would write against these stored memories.

Rules, most important first:

1. Be exact. State each fact with the speaker's own specifics. Never swap in something similar: a cello is not a violin, "a lighthouse on a cliff" is not "a lighthouse in Cornwall", "about six months" is not "a year". Never turn a list into a general category, and keep every item of a list. Never add a detail the transcript does not say. When in doubt, use the speaker's own words.
   Session date: 12 March 2024. Transcript: "D4:3 Priya: I've been learning the cello for about six months. I practise Tuesdays and Saturdays, mostly Bach suites, and my neighbour's kids come to listen."
   Wrong: "Priya is learning to play a string instrument and enjoys classical music."
   Wrong: "Priya has been learning the violin for a year."
   Right: "Since about September 2023, Priya has been learning the cello. She practises on Tuesdays and Saturdays, mostly Bach suites, and her neighbour's kids come to listen."

2. Never leave a relative time in a memory. Words such as "yesterday", "today", "tomorrow", "the previous day", "last week", "this weekend", "next month", "recently", "a few days ago" or "two years ago" mean nothing months later, so replace each with the date it refers to, worked out from the session date. The memory then states only that date: do not also write the session date beside it, and never start a memory with "As of". Write dates in words ("3 October 2023"), never as numbers ("2023-10-03"), even though the stored memories show them as numbers.
   - An event is dated with the day it happened or is planned for, e.g. "On 3 October 2023, ...". An event said without a time happened on or around the session date.
   - A time that cannot be pinned to one day is written as a period, e.g. "the week before 4 October 2023", "in September 2023" or "in 2021".
   - An ongoing state, such as a habit, a preference or how long something has gone on, says when it began if the message tells, e.g. "since about April 2023" rather than "for about six months". Otherwise end it with "(mentioned on <session date>)".
   With session date 4 October 2023, a Wednesday: "yesterday" is "on 3 October 2023", "tomorrow" is "on 5 October 2023", "last Friday" is "on 29 September 2023", "last weekend" is "the weekend of 30 September and 1 October 2023", "last week" is "the week before 4 October 2023", "next month" is "in November 2023", "two years ago" is "in 2021", and "for about six months" is "since about April 2023".
   Session date: 4 October 2023. Transcript: "D7:1 Rosa: Yesterday I finally met the luthier in Cremona who made my viola."
   Wrong: "As of 4 October 2023, Rosa met the luthier in Cremona who made her viola the previous day."
   Wrong: "On 4 October 2023, Rosa met the luthier in Cremona who made her viola."
   Right: "On 3 October 2023, Rosa met the luthier in Cremona who made her viola." with "occurred_at" "2023-10-03".
   Session date: 4 October 2023. Transcript: "D7:5 Rosa: My recital is tomorrow and I'm so nervous."
   Wrong: "As of 4 October 2023, Rosa's recital is tomorrow and she is nervous."
   Right: "Rosa's recital is on 5 October 2023. On 4 October 2023 she said she was very nervous about it." with "occurred_at" "2023-10-05".

3. Keep the small things as memories of their own: the reasons people give, how they felt, how often or how long they do something, and what someone says when the other person asks them something. A reply to being asked is often the most important thing in a session to remember, even when it is short, e.g. "We only go once or twice a year" or "I left because the job didn't match my values".

4. One memory states one specific thing and cites the few messages it comes from, usually one to three. Do not write summaries such as "Both of them value family" or "Caroline and Melanie caught up about their week" that cite many messages but state nothing specific; write the specific facts instead, each as its own memory.

5. Never lose a specific that is already stored. A stored memory is not replaced by a vaguer one: every memory you write that supersedes or adds to a stored memory keeps the dates, names, places, list items and quantities it is about. Never generalize a dated event into a habit or a summary.
   Stored: "M2.4 | 2022-04-03 | Tomás visited Lisbon on 3 April 2022 and stayed with his aunt Inês."
   Transcript: "D5:2 Tomás: I love travelling. Peru and Japan were amazing too."
   Wrong: a memory "Tomás loves to travel and has visited Portugal, Peru and Japan." that supersedes M2.4.
   Right: a new memory "Tomás loves travelling and has been to Peru and Japan (mentioned on 20 June 2023)." that supersedes nothing, since M2.4 is still true.

6. Account for every message worth remembering. Go through the transcript message by message: each message that says something worth remembering must be cited by a new memory or listed in a duplicate's "source_dia_ids". A stored memory about the same person or topic is not a reason to skip a message. If the message has any specific the stored memory lacks, such as a name, an item, a date, a reason, a feeling or a reply, write a memory for it. When unsure whether something is already stored, write the memory: a repeated memory costs little, a lost one cannot be recovered.

7. Leave out greetings, small talk and anything not worth remembering.

How to use the stored memories:
- List a stored memory under "duplicates" only when it already states every specific the message says, so a new memory would add nothing. Being about the same topic does not make it a duplicate. Never write a memory that restates a stored one and supersedes it.
- If the session adds new details about something stored, write a new memory with only the new details. Do not merge the old and new into one combined memory, and do not supersede the stored memory: it is still true.
- Supersede a stored memory only when it is no longer true: a plan was carried out or cancelled, someone moved, changed jobs, ended a relationship or changed their mind. Then write a new memory stating the new situation and when it changed, keeping every specific of the stored memory that still holds, and put the stored memory's id in its "supersedes".
- Only use ids from the stored memories listed above.

Return a JSON object with three lists, "entities", "memories" and "duplicates".

"entities": every person, place, organization, pet, object or other thing that one of your memories is about. Each has:
- "id": a short lowercase id such as "caroline" or "support-group". Reuse the id of an entity recorded earlier only when it is exactly the same thing, e.g. the same person or the same pet. Anything else - a different object, place, group or event, even a related one - gets its own new entity with its own id. Never give one thing two ids, and never use one id for two things.
- "name": its name as said in the conversation.
- "kind": what sort of thing it is, such as "person", "place", "organization", "pet", "event" or "object".
Every id used in a memory's "entities" or "relationships" must be either in the list of entities recorded earlier or declared in this reply's "entities". Declare an entity before you use it.

"memories": the new memories to store. Each has:
- "content": one or a few sentences stating the memory, following the rules above. Name people instead of using pronouns.
- "memory_type": "fact" for a lasting fact about someone or something, "preference" for a like, dislike, opinion or wish, "event" for something that happened or is planned at a particular time, "note" for anything else.
- "occurred_at": for an event, the date of the event itself, as an ISO 8601 date or date-time (e.g. "2023-05-07"). This is often not the session date: something that happened "last week" happened before it, and something planned for "next month" comes after it. For a period, such as "the week before 16 June 2023", use the first day of the period ("2023-06-09"). If the date of the event cannot be worked out, use null rather than the session date. For anything other than an event, null.
- "entities": the ids of the entities the memory is about.
- "relationships": links between those entities that the memory states, each with "subjectEntityId", "predicate" (a short verb phrase such as "sister_of", "lives_in" or "adopted"), "objectEntityId" (an entity id, or null when there is no object) and "kind": "fact" when stated as true, "hypothesis" when guessed or uncertain, "rumor" when heard from someone else.
- "source_dia_ids": the message ids from this transcript that the memory comes from.
- "supersedes": the ids of stored memories that this memory replaces because they are no longer true, or [] when it replaces none.

"duplicates": stored memories that this session only repeats, with nothing new. Each has "memory_id", the stored memory's id, and "source_dia_ids", the message ids from this transcript that repeat it. Do not also write a memory for them.
